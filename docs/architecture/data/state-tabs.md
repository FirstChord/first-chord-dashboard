# State Tabs Schema

Last updated: 2026-08-10

This note is the canonical map for dashboard-owned state lanes. It documents the Google Sheets tabs that store workflow state, cache snapshots, append-only logs, or derived context. It is intentionally about dashboard state, not the main `Students` operational sheet.

## Principle

External systems own external truth. The dashboard stores workflow state, action history, cached snapshots, and derived context that helps humans close loops.

**Sheets/database boundary:** Sheets remains the general workflow store because
humans can inspect and correct its human-paced lanes. PostgreSQL has two bounded
responsibilities: the unique Practice Chat delivery claim committed before
provider work, and the rebuildable event-grain MMS lesson mirror used to prove
parity before any source cutover. It is not a wholesale replacement for Sheets,
and the mirror is not schedule truth. New event-heavy/machine-generated state
must justify its concurrency, growth, correction, backup, and recovery model; use
[the storage boundary](./storage-boundary.md) and sheet census rather than adding
another tab or broad database layer by instinct.

Lane meanings:

- `truth` = primary operational truth owned by a source system, usually outside this table
- `cache` = dashboard-held snapshot of external truth
- `workflow-state` = current state for a human/admin loop
- `append-only-log` = audit/history; do not rewrite rows
- `derived-context` = dashboard interpretation that reduces guessing but is not source truth

## Tabs

| `Schedule_Context` | cache | Cached selected MMS schedule facts per student | `mms_id` | keyed upsert | `upsertScheduleContextRow` | Snapshot/cache, not truth. Refresh from MMS when a student is new or a slot changes. MMS calendar timestamps represent lesson wall-clock values: derive weekday/time from their written date and time, never from the server or developer machine timezone. |
| `Parent_Understanding_State` | workflow-state | Parent check-in campaign workflow state | `student_mms_id` | keyed upsert | `upsertParentUnderstandingStateRow` | Manual, approval-first. Does not auto-send WhatsApp, edit MMS, or notify tutors. |
| `Student_Portal_Access` | workflow-state + sensitive access configuration | Per-student notes-protection rollout, encrypted memorable code, credential version, staff claim, and WhatsApp confirmations | `student_mms_id` | keyed upsert | `upsertStudentPortalAccessRow`, `POST /api/admin/student-notes-rollout`, onboarding follow-up creation | A missing row deliberately preserves legacy public notes during the phased rollout. `protection_enabled = TRUE` makes the public notes API require a signed one-year device cookie. The code is encrypted for authenticated-admin handover and separately stored as a secret-peppered verifier; plaintext must never enter logs or cached page data. “Message sent” is an explicit human confirmation, not provider delivery evidence. |
| `Cover_Bank_State` | workflow-state | Tutor cover-availability phone survey (willing yes/no, days, same-day-vs-notice, notes) | `tutor_key` | keyed upsert | `upsertCoverBankStateRow` | `tutor_key` is the internal short name (matches `ADMIN_TUTORS`) or `ext:<slug>` for external cover-bank tutors, who exist only as rows here. Availability is what the tutor *said* on the call; teaching days come live from `Schedule_Context` at read time and are never stored here. |
| `Tutor_Absence_State` | workflow-state | Tutor absence workflow decisions/messages | `absence_id` | keyed upsert | `upsertTutorAbsenceStateRow` | Absence workflows should end in cover or cancellation decision plus parent-message tracking. Long-absence capture previews MMS across a date range, then still writes one normal per-date absence record. Cancelled days also auto-create idempotent structured pause `Planning_Items` per affected student unless payment is explicitly marked not-needed for that lesson; the undated `Students.payment_expectation = stripe_paused_expected` flag is context and does not suppress this dated work. Repeated cancelled dates for the same student are grouped into an away-period pause plan; when the period expands, superseded single-lesson or shorter-period plans are parked, not deleted. Parent communication can be grouped by student/period, but stored workflow state remains per dated absence so finance, payment handling, and audit trails stay precise. |
| `Planning_Items` | workflow-state | Brain/planning capture for ideas, actions, initiatives, learning notes, and strategic notes | `planning_id` | keyed upsert | `upsertPlanningItemRow` | Human-created work, not system-detected issues. Can link to students/tutors/workflows. Onboarding deliberately adds two deterministic Action families: `planning_first_lesson_checkin_<mmsId>` after core setup, and `planning_early_stripe_timing_<mmsId>` only when lesson one is at least seven days away; repeat onboarding upserts rather than duplicates. Open first-lesson cards compose a read-only lesson/payment/access evidence strip and durable human confirmations from `Planning_Progress_Log`; they cannot become `done` before the follow-up date or until continue/stop, payment handling where required, WhatsApp membership, and student access are complete. The early Stripe card is a human review reminder, never provider truth or authority to mutate Stripe. The ordinary UI calls `initiative` **Project**, `action` **Action**, and `idea` **Note / idea**; stored values remain unchanged. A Project owns an outcome/context and may have several dated Action children via `parent_planning_id`; the child rows' open/done states are the progress record, so ordinary Project work does not require duplicate manual progress reports. A Project cannot be marked done while linked Actions remain open. Friday-reflection children keep their existing link but are excluded from Project semantics. New Ideas and legacy learning/strategic notes share the **Let's work on the school** view; an Idea can be converted in place to an Action or Project. `parked` is the soft-delete/archive state: keep the history, remove from active work, and do not let parked pause cards drive finance pause forecasting. `owner` ∈ `Unassigned`/`Finn`/`Tom`/`Fennella` (assignment; a "Fennella" planning filter surfaces her items — Fennella currently logs in via the shared admin identity, own auth deferred). `plan_mode` remains `task` / `ongoing` for compatibility but is derived for ordinary kinds: Project → `ongoing`; Action and Note / idea → `task`. Dedicated legacy note/workflow rows may preserve an explicit mode. The same `target_date` column reads optional **Review next** on a Project and **Do on** on an Action; manual active Actions require a date, while unscheduled Actions remain in Inbox. `is_pause` ∈ `true`/`false`/`''`: explicit pause classification set by the plan panel's Structured pause / General toggle. **Flag-then-infer** — an empty value (legacy rows, auto-created pause plans) still infers pause-ness from the title/notes wording exactly as before, so it's backward compatible; a set value overrides both `isPausePlanningItem` (UI) and the pause forecast (`is_pause = false` drops a card from the forecast even if its old notes still say pause). |
| `Planning_Progress_Log` | append-only-log | Append-only progress history for planning items | `progress_id` | append-only | `appendPlanningProgressLogRow` | Momentum and controlled workflow-step log. Do not overwrite history. First-lesson confirmations use versioned `First lesson loop v1:` markers with `progress_type = workflow_step`; latest value per step wins, so an undo appends a correction instead of rewriting the audit trail. These markers are hidden from the ordinary “Latest progress” prose panel. |
| `Practice_Notes_Log` | append-only-log + workflow-state | Practice Chat lesson-note memory, portal note read source, Level 2 delivery audit/idempotency state, and reviewed note-to-song learning evidence | `note_id` for snapshots; `delivery_key` for Level 2 delivery records | snapshots append with duplicate guard; Level 2 delivery rows upsert by `delivery_key`; portal reads select latest sent/completed row first, then fall back to MMS | `appendPracticeNoteLogRow`, `upsertPracticeNoteLogRow`, `getPracticeNoteLogRows`, `POST /api/practice-notes`, `POST /api/practice-notes/mms-test`, `GET /api/notes/[studentId]`, `GET /api/student-portal/[studentId]/notes` | Dashboard-owned learning/context memory. Optional `song_ids_json` holds up to twelve tutor-confirmed catalogue IDs; `song_titles_json` is a capture-time readability snapshot, `unlisted_song_titles_json` holds up to six reviewed raw observations that are not Song facts, and `song_link_version` records the contract. Both note routes reject unknown catalogue IDs. Deterministic exact-title proposals remain unchecked until the tutor selects them; blank means no explicit evidence—not “no song”—and sentiment is never inferred from prose. New Level 2 rows also include a self-attested `acting_tutor` (matched against the student's one clear recorded tutor; not verified identity), selected MMS attendance ID/event ID, target-selection reason, recipient, Gmail message/thread ID, send status, sent timestamp, email error, manual follow-up state, `operation_status`, and `completed_at`. The execute route must save a claim before MMS or Gmail work; claim failure is a 503 with no provider action. `practice_note_delivery_claims` in PostgreSQL is the transactional claim store and enforces a unique `delivery_key`; Sheets remains the audit/read model, not the lock. A failed final log is explicit partial success, not proof that provider work failed. Sent/completed rows are parent-visible only through the dedicated portal notes API; they are never embedded in initial profile HTML or metadata. Draft/in-progress/failed snapshots are not parent-visible. MMS remains fallback and attendance/payroll continuity source. Rows with `manual_follow_up_needed = TRUE` surface as `practice_delivery` issues in the Issue Queue; the issue quick action clears the flag with a single-cell write (a full-row upsert would blank the columns `normalisePracticeNoteLogRow` does not map). |
| `Practice_Chat_Sessions` | append-only-log | Practice Chat **attempt** telemetry for the six-week evaluation: one row per opened ritual, finished or not | `session_id` | keyed upsert by `session_id` (three writes per session: opened → note_generated → finished) | `upsertPracticeChatSessionRow`, `POST /api/practice-chat-sessions`, `POST /api/notes/[studentId]/prior-rating` | Exists because `Practice_Notes_Log` only gains a row when a tutor reaches the end, so abandonment, retries, transcription failures and pre-save edits are invisible there by construction. **Carries no audio, no transcript and no note text** — durations, counts and flags only, plus one ≤200-char comment a tutor chose to write. That keeps its sensitivity below `Practice_Notes_Log`'s and lets it be purged on its own schedule when the evaluation ends. **Abandonment is derived at read time**, never written: a client that died cannot report that it gave up, so `deriveSessionOutcome` treats a non-`finished` phase older than `ABANDONED_AFTER_MS` as abandoned and reads `last_step` for where. Three fields are deliberately kept apart because conflating them would libel a careful tutor: `asr_error_count` (the tool failed), `re_record_count` (the tutor chose to redo an answer), and `note_edited`/`edit_char_delta` (the tutor improved the output). `ms_active` is the friction measure; `ms_session_total` is contaminated by panels left open mid-teaching and is context only. `rating_accuracy`/`rating_comment` are self-reported by the tutor who taught the lesson and must never be merged with observed columns in a report. Writes are best-effort from the PWA and must never fail a lesson. Telemetry is written only when the launch URL carried `studentId` + `dashboardBaseUrl`, so a bookmarked or installed PWA records nothing. **`POST /api/notes/[studentId]/prior-rating` is the one write on the per-student tutor-token boundary**, which is otherwise deliberately read-only until tutor auth exists. It is admitted because it is not consequential in the sense that rule protects: it validates a 1–5 answer server-side, writes it to one telemetry row, and touches no provider, no parent-visible record and no workflow state. It resolves its own target (the student's latest finished, unrated session) so the client cannot name a row, and a repeat tap finds nothing to rate rather than overwriting. Pinned by `tests/admin/notes-summary-route-boundary.test.mjs`; a second write on that route should have to be argued for. |
| `Communication_Log` | append-only-log | Passive record of parent messages copied to send from the dashboard | `message_id` | append-only (dedup by student+body within a short window) | `appendCommunicationLogRow`, `logCommunication`, `POST /api/admin/communications` | Record-only logbook, written as a fire-and-forget side-effect of existing "Copy message" buttons. Copied does not prove sent. No approval, no sending. Does not change any workflow. |
| `Incoming_Message_Inbox` | workflow-state | Review inbox for inbound parent/tutor messages auto-captured from confirmed WhatsApp lesson groups, with manual-paste fallback | `incoming_id` | keyed upsert by deterministic source/chat/message identity; admin hard-delete only for test/noise rows | `upsertIncomingMessageInboxRow`, `deleteIncomingMessageInboxRow`, `captureIncomingMessage`, `correctIncomingMessage`, `snoozeIncomingMessage`, `convertIncomingMessageToPlanning`, `POST /api/admin/incoming-messages` | Intake lane only. Classification has separate topic, intent, actionability and confidence/evidence fields. `proposed_*` plus `classification_version` preserve the machine output; `suspected_category`/`classification_actionability` hold the current human-final interpretation; `classification_decision` is `unreviewed`, `accepted`, `corrected`, or `legacy`. Only accepted/corrected rows feed reviewed-topic learning signals. An auto-captured row stays open for `action_needed`/`reply_needed`, goes to `needs_review` for `uncertain`, and is pre-archived only for `no_action`; none authorises a payment, pause, send, attendance, or provider action. `resolution_type` distinguishes linked planning, handled-no-plan, and ignored-no-action outcomes. `snoozed_until` is a wake-up time on an otherwise-open row: **Later** hides it from today's inbox and Overview count without resolving it, and an expired time makes it visible again on the next read. Done/no-action/correction/conversion clear the snooze. Every readable open row retains **Reply + Plan**, whose pre-write preview contains proposed type/student, editable extracted dates, and one bounded admin-reviewed reply. The reviewed dates and exact reply feed the idempotent `planning_<incoming_id>` draft; **Copy reply & open plan** archives/links the inbox row only after the Planning write succeeds. The reply remains in Planning notes and, for structured pauses, becomes the final WhatsApp handoff after payment work. Copying is logged but never proves sending; the pause completion gate still requires human sent-confirmation. **Reply** remains the separate one-card AI/deterministic path and creates no plan. A later school-side chat message is weak engagement evidence on the nearest preceding open row only, not proof of reply or resolution. Every human review stamps actor/time. External bridge writes require `INCOMING_MESSAGE_INGEST_SECRET`. |
| `WhatsApp_Group_Map` | workflow-state | Human-reviewed map of WhatsApp lesson groups observed by the incoming-message bridge | `chat_id` | keyed upsert by WhatsApp chat ID | `upsertWhatsappGroupMapRow`, `captureIncomingMessage`, `correctIncomingMessage`, `syncWhatsappGroups`, `reviewWhatsappGroup`, `POST /api/admin/incoming-messages` | Unreviewed group IDs are matching hints only. Bulk `mode: sync_groups` proposes groups/matches; `mode: review_group` confirms or ignores them. A confirmed group map is the server-checked gate for automatic capture and high-confidence matching, and stores selected student context (`matched_mms_id`, `matched_fc_id`, parent name/phone, tutor, instrument, `confirmed_by`, `confirmed_at`); a sync never downgrades a confirmed group. `status` values: `review` / `confirmed` / `ignored`. Sibling groups hold extra students in `additional_mms_ids` (comma list, added manually via `mode: add_group_student`); matching then disambiguates by the student named in each message and asks for manual review when nobody is named. Renamed groups, old students, and changed tutors need human review before continued reliance. |
| `Proposals` | workflow-state | Generic "machine prepares, human commits" store; V1 lane `incoming_reply` = suggested WhatsApp replies for open `Incoming_Message_Inbox` rows | `proposal_id` | keyed upsert | `upsertProposalRow`, `draftIncomingReplyProposal`, `decideIncomingReplyProposal`, `POST /api/admin/incoming-messages/reply-proposals` | One open proposal per `linked_id`: a redraft supersedes, never duplicates. `status` ∈ `proposed`/`approved`/`rejected`/`expired`/`superseded`; expiry (7 days) and supersession (message text changed under the proposal, detected via `sourceTextHash` in `evidence_json`) are **derived at read time** (`deriveEffectiveProposalStatus`) and persisted lazily on the next write — a page load never mutates the tab. `evidence_json` holds the source-text hash, bounded policy/model context and fact IDs, but deliberately not another copy of the parent message; `applied_body` is the text the human actually used, so used-unmodified vs edited telemetry (`summariseProposalTelemetry`) needs no extra column. Approving logs to `Communication_Log` (source `incoming_reply_proposal`) — copied still does not prove sent. Drafting happens only when the human presses **Reply** on one exact card, behind `ADMIN_AI_REPLY_DRAFT_ENABLED`; there is no bulk/background producer. Ambiguous messages get a deterministic neutral draft with no model call (`created_by` = `policy_fallback`). Contract: `docs/architecture/ai/tool-contracts.md` → `incoming_reply_draft.propose`. |
| `Bridge_Status` | workflow-state | Heartbeat row(s) from the local WhatsApp bridge so "down" and "connected but capturing nothing" are visible on the dashboard | `bridge_id` | keyed upsert (one row per bridge, currently `primary`) | `recordBridgeStatus`, `POST /api/admin/incoming-messages` (`mode: bridge_status`, bridge secret) | Written every ~30min + on connect (`BRIDGE_HEARTBEAT_MS`). `assessBridgeHealth` warns when the heartbeat is >2h old, the confirmed-group list is empty, or no auto-capture has landed for 3+ days; rendered as a one-line strip on the inbox page and an amber card on `/admin`. Fail-silent on the bridge side — a Sheets hiccup never affects capture. Not source truth for anything; purely observability. |
| `Students_Archive` | append-only-log | Archive copy before dashboard-driven student removal from `Students` | inherited student row plus archive metadata | append-only | `archiveAndDeleteStudentSheetRow` | Safety record for destructive student removal. Metadata columns: `archived_at`, `archived_by`, `archive_note`, and `date_left` (the `YYYY-MM` month the student left, captured by the one-click "Mark student as left" action — feeds roster-movement / "when did billing stop"). Column self-heals on next archive write. |
| `Tutor_Lifecycle` | workflow-state | Human-approved availability of a generated tutor identity for live operational use | `teacher_id` | keyed upsert | `/admin/tutors`, `saveTutorLifecycle` | `ADMIN_TUTORS` remains the identity/teacher-ID source, including former tutors. A missing lifecycle row means `active`; `leaving` remains selectable until a human retires it; `retired` is hidden from live tutor dashboard, onboarding, capacity, waiting-list, planning and new absence choices. Retirement never deletes identity, historical absence/planning records, or payroll runs. The dashboard presents handover warnings (assigned students, cached future lessons, unpaid payroll, open planning/absence records) but does not block retirement. |
| `Student_Lifecycle` | cache | How long each student has been with the school: first and last lesson, tenure or lifetime, lessons attended | `mms_id` | full replace on explicit refresh | `npm run lifecycle:refresh --apply`, `replaceStudentLifecycleRows` | Derived from MMS attendance, which reaches back to 2019 and is the only record of the school's own past. Refreshed deliberately, never on page load. Exactly one of `tenure_years` (still here) or `lifetime_years` (left) is populated; blank is meaningful. `departed` requires inactive **and** nothing booked — inactive with future lessons is a pause, not a leave. A student with only future lessons has no `first_lesson` and no tenure, because a booked lesson has not started any clock. |
| `Lifecycle_Snapshot` | append-only-log | One row per lifecycle refresh: school-level tenure, lifetime, early-departure counts, and calendar-marking completeness | `snapshot_at` | append | `appendLifecycleSnapshotRow` | The memory `Student_Lifecycle` deliberately lacks. Its sibling is fully rebuildable from MMS; these rows are not — each measures a moment that has passed. Mirrors `Finance_Snapshot`. Read by humans during the termly ritual; nothing acts on it automatically. A successful `--apply` run books its own next prompt as the single `planning_student_lifecycle_review` row in `Planning_Items` (same self-renewing pattern as the Sheets backup), because a snapshot lane with one row is not a trend. Deliberately **not** a cron or scheduled Action: the value is in a human reading the report, an unattended nightly job would fill this lane with noise, and it would need the MMS token as a CI secret for no gain. `marking_completeness_pct` is the share of past lessons carrying a definite attendance status over the trailing twelve months — present, absent-with-notice, teacher-absent, anything. **A marked absence counts as a success**: the metric is engagement with the calendar, not attendance rate. Only `Unrecorded` and blank are unmarked, the same boundary `resolveSlotState` uses to gate payroll. Lessons inside `MARKING_MATURITY_DAYS` (14) are excluded, since they may legitimately not be marked yet and would otherwise put the figure permanently out of reach. It sits beside the retention columns because it validates them: retention depends on knowing when a student stopped, which depends on the register being kept, so if this falls the columns to its left degrade silently. Measured 73% (2019) → 22% (2021) → 31% (2023) → 50% (2024) → 87% (2025) → 90% (2026); the step change follows MMS attendance becoming the basis for tutor pay in 2024. |
| `Tutor_Pay` | workflow-state | Finance/payroll pay assumptions, including sensitive salary rows, invoice cadence, and payroll-active flag | `tutor` | keyed upsert/manual sheet edit | `upsertTutorPayRow`, Finance sheet edits | Private finance config. Salaries must stay in Sheets/Railway runtime surfaces, not committed to git. Blank `invoice_cadence` defaults to weekly; biweekly/fortnightly tutors should be marked explicitly. |
| `Expenses` | workflow-state | Recurring fixed-overhead assumptions used by the finance run-rate | `name` | keyed upsert/manual sheet edit | `upsertExpenseRow`, Finance sheet edits | This is for recurring monthly/weekly/annual assumptions such as rent, software, insurance. It affects estimated margin. The old `General` buffer is ignored if present because miscellaneous spend now lives in `Expense_Log`. |
| `Expense_Log` | append-by-default log | Actual spend memory for one-off or variable card/bank spending | `expense_id` | append by default; admin delete only for mistaken entries | `appendExpenseLogRow`, `deleteExpenseLogRow`, `/admin/finance` add-spend form | Use for paint, repairs, staff coffees/lunches, one-off room improvements, etc. Reconcile against the bank account at month-end and add missing lines. Month-to-date totals reset by calendar month and are included in finance snapshots as separate cash-view fields. Deletion is a correction path for accidental entries, not normal editing. |
| `Finance_Snapshot` | append-only-log + derived-context | Dated finance run-rate snapshots | `snapshot_id` | append-only | `appendFinanceSnapshotRow`, `/api/cron/finance-snapshot` | Estimate series, not accounting. Includes run-rate fields plus the `Expense_Log` total known at capture time. It is not a month-close record: spend entered after the last weekly capture remains authoritative in `Expense_Log` and is read from there, never backfilled into an immutable snapshot. Weekly rows keep timestamped IDs; a monthly baseline has the deterministic ID `fs_monthly_YYYY-MM`. The workflow retries on days 1–7, but the first successful row wins and keeps its real capture timestamp; retries must never fabricate or backdate a missed month. |
| `Payroll_Runs` | workflow-state + append-by-period ledger | Tutor payroll review/payment state for each tutor and pay period | `payroll_id` | keyed upsert by tutor+period | `upsertPayrollRunRow`, `/admin/finance/payroll` | V1 reconciliation ledger, not bank/payment truth. MMS attendance remains the source for lesson attendance; `Tutor_Pay` supplies rate/cadence; this tab stores Tom/Finn review status, paid status, adjustments, invoice status, and notes. **Tutor confirmation (Phase 2):** `tutor_response` ∈ `''`/`confirmed`/`disputed`, `tutor_responded_at`, `tutor_note` — written by the tutor via the public signed statement link (`recordTutorStatementResponse`, no login; the token is the identity). A `disputed` reviewed row is held out of the Wise batch (`selectPayableReviewedRuns`) until the tutor confirms the resolved statement. Saving a material statement change (period, lesson basis, amount or payment route) clears the old response and sent marker; admin-only notes/invoice tracking do not. Confirmation never moves money — the admin still approves the batch. The same signed link is also the tutor's printable record: while reviewed it renders a referenced **Payment statement** with issue/confirmation dates; after the run is marked paid it renders a **Payment receipt** with the paid date. `Print or save PDF` uses the browser print surface so the tutor can retain a permanent copy before the 30-day bearer link expires. This payer-issued record deliberately does not claim to replace a freelancer invoice. |
| `Tutor_Phones` | reference (sensitive) | Tutor WhatsApp numbers so a tutor's own reply in a lesson group is recognised as school-side (reply evidence) instead of a mis-classified parent inbox row | tutor name | manual sheet edit only | `getTutorPhoneRows`, `captureIncomingMessage` | Personal data — lives only in Sheets, never committed to git (same rule as salaries/Wise). Human-maintained; **read tolerantly** (`getTutorPhoneRows` matches the name/phone columns by trimmed, lower-cased header, so the exact header wording isn't a contract) and a missing tab simply turns tutor recognition off. A matched tutor message stamps open items as reply evidence (`school_replied_by` = tutor name); it never creates a row, never classifies, and never marks anything handled (only Finn/Tom stamping done does). |
| `Tutor_Wise` | reference (sensitive) | Wise batch-payment recipient details per tutor, used to generate the Wise CSV | `tutor` | manual sheet edit only | `getTutorWiseRows`, `/admin/finance/payroll/wise-csv` | Sensitive recipient data — lives only in Sheets/Railway, never committed to git (same rule as salaries). Read-only from the dashboard; populated by hand. `tutor` must match the tutor's short name (the `ADMIN_TUTORS` key, e.g. `Kenny`) or full name (e.g. `Kenny Bates`) as shown on the payroll cards — **not** `Tutor_Pay`, which only holds salaried owners + overrides. `buildWiseBatch` joins on `tutorShortName` then `tutor` (full name). Prefer storing only the opaque `recipient_id`; `recipient_detail` (raw bank numbers) is optional if Wise pays the saved recipient by id. |
| `Stripe_Amounts_Cache` | cache | Per-student Stripe subscription billing amounts (the finance estimate's "actuals" feed) | `mms_id` | full replace each refresh | `replaceStripeAmountsCacheRows`, `/api/cron/stripe-amounts` | Rewritten wholesale on the first of each month and every Monday (row set follows the roster; per-row upserts would crawl). Consumers apply a 14-day staleness guard (`buildStripeAmountsMap`): a dead workflow degrades students back to the price-table estimate, never blocks the page. Live Stripe truth stays in Stripe. |
| `Stripe_Forecast_Monthly` | append-only-log + derived-context | One immutable dashboard-only Stripe collection forecast per calendar month, including compact per-student evidence | `month` (`YYYY-MM`) | first row wins; never update | `appendStripeForecastMonthlyRow`, `/api/cron/stripe-amounts` before provider reads | Built from the operational roster, dashboard price table, payment expectation, cached MMS schedule weekday, lesson frequency, and structured Planning pause windows. It accepts no Stripe amount/invoice input. The Stripe cron must durably find or append this row before it may fetch subscriptions or invoices; a forecast write failure therefore blocks the provider reveal. `items_json` makes aggregate cancellation detectable without adding a high-volume detail tab. ## Read-only derived views

`/admin/insights` is a rolling 30-day **read-only** view over `Practice_Notes_Log`, `Parent_Understanding_State`, `Incoming_Message_Inbox`, and `Communication_Log`. It owns no state and writes no history. ## Format Contracts

Some source formats are fragile because they come from human-edited external systems. Do not change these without updating the relevant parser/tests:

- MMS sign-up form labels `Preferred days` and `Preferred times` feed waiting-list availability matching. If the MMS form wording changes, update the waiting-list parser/tests before relying on capacity hints.
- The Google Sheets `Students` header row is a contract for dashboard reads, FC regeneration, backups, and archive/delete flows. Protect the header row in Google Sheets with an edit-warning. If a column is renamed or moved, update the readers/tests intentionally.
- **Students tutor banners are merged cells, not blank rows.** The `Students`
  tab groups students under orange tutor bars (`MICHAEL GEMMELL`), and each bar
  is a merged range **two rows deep across columns A–I**. The bar's second row
  looks like an empty student row and is not one: writes to A–G there are
  accepted by the Sheets API — `updatedCells` counts them — and hold nothing,
  while columns J onward lie outside the merge and do persist, producing a
  half-written row. Never write a student into the row directly beneath a
  banner. Add rows through `addStudentSheetRow`
  (`lib/admin/sheets/students.mjs`), which calls `insertDimension` to create a
  genuinely new row rather than filling apparently blank cells. The banners are
  cosmetic to every reader: `mapRowsToObjects` keeps them (they are not wholly
  empty) and the student assembly then drops them for having no `mms_id`.
  Note also that `findTutorInsertRow` (`lib/admin/sheets-helpers.mjs`) appends
  at the **bottom of the sheet** for a tutor with no existing rows, so a new
  tutor's first student lands outside their banner block until one row is moved
  under it by hand.
- **`Waiting_List_State.updated_at` is the growth clock.** Monthly joiner counts
  come from `buildRosterMovement` (`lib/admin/roster-movement.mjs`) over rows
  with status `onboarded`, bucketed by `updated_at` (falling back to
  `date_started`) — **not** by the first lesson date. A student onboarded on 31
  August who starts on 9 September counts as an August joiner. Two consequences:
  a student recorded outside the dashboard onboarding flow is not counted at all
  until a row exists, and a returning student re-onboarded by hand needs one
  written deliberately. Historical departures use `Students_Archive.date_left`,
  then an explicit month and year in a legacy `archive_note`, and only then fall
  back to `archived_at`. This keeps an old departure out of the month when its
  cleanup happened without rewriting the append-only archive. A student removed
  outside the archive flow is likewise uncounted. Finance snapshot period counts
  continue to use the exact `archived_at` action timestamp because `date_left` is
  only precise to a month.
- **Incoming-message classification fields.** `Incoming_Message_Inbox` retains
  immutable machine proposals in `proposed_category`, `proposed_intent`, and
  `proposed_actionability`; the current reviewed values live in
  `suspected_category` and `classification_actionability`.
  `classification_decision` is one of `unreviewed`, `accepted`, `corrected`, or
  `legacy`. Do not overwrite proposal fields during review or count untouched
  rows as labelled truth. Actionability values are `action_needed`,
  `reply_needed`, `uncertain`, and `no_action`.
- **Tutor names are not a stable key.** The school records tutors under two
  forms and always has: the tutor surface and `Song_Assignments.assigned_by` use
  the short name (`Calum`, `Dean`), while `Practice_Notes_Log.tutor_name` often
  carries the full name (`Calum Steel`, `Dean Louden`) — and **both forms appear
  inside the same column**. Any view gathering across lanes must resolve through
  `resolveTutorName` (`lib/admin/tutor-identity.mjs`), which looks names up in
  the canonical `ADMIN_TUTORS` roster and returns an unrecognised name unchanged
  rather than approximating it. Song teaching history shipped without this and
  showed "Calum, Calum Steel +1 · 2 students" — one human counted twice. Note
  that `acting_tutor` is a *label* (`Self-attested: Calum`), not a name: never
  copy it into an identity column.
- **Practice Note song links.** `Practice_Notes_Log.song_ids_json` and
  `song_titles_json` are JSON arrays with matching order and at most twelve
  values. `unlisted_song_titles_json` holds at most six tutor-confirmed raw
  titles that are explicitly not catalogue facts; `song_link_version` is `2`
  for this contract. Submitted IDs are revalidated against the repository
  catalogue. The PWA may propose deterministic exact-title matches from note
  text, prioritising the current shelf, but a tutor must select a proposal
  before it is written. Duplicate titles are not guessed and one-word titles
  require a song-work cue. Never treat an unreviewed proposal or unlisted title
  as a stable song join.
- **Practice Chat session evidence classes.** `Practice_Chat_Sessions` mixes three
  kinds of claim in one row and any report over it must keep them apart, because
  the brief they answer asks for all three and they are not equally trustworthy.
  **Observed** (the system saw it happen): every `ms_*`, `*_count`, `phase`,
  `outcome`, `note_edited`, `prior_history_opened`. **Human-rated** (a tutor
  said so): `rating_accuracy`, `rating_comment`, `prior_usefulness` — always
  shown with their n, never averaged into an observed rate. **Derived** (a rule
  guessed): abandonment, and "a next practice action was captured", which is
  `practice_goals` being non-empty in the joined note — a text rule, not an
  observation. `steps_json` is a compact per-question array
  (`[{q, recordMs, transcribeMs, chars, errors, skipped, reRecorded}]`), the same
  "evidence without a high-volume detail tab" pattern as
  `Stripe_Forecast_Monthly.items_json`; it is bounded at three entries because
  the ritual has three questions. Timestamps inside a session come from the
  tutor's browser and are only ever used as deltas within that session — a
  skewed machine clock cannot distort a duration. Anything compared across
  machines uses `created_at`, stamped server-side on receipt.
- **Practice Note markup.** The note stored in `Practice_Notes_Log.raw_note_text`
  is plain text carrying three markers: `**bold**`, `_italic_`, and `- ` at the
  start of a line for a bullet. They are produced by Practice Chat
  (`public/src/note-markup.js`) and understood by every renderer here
  (`lib/notes-markup.mjs`, used by the parent email and the MMS
  `StudentNote`, plus `components/shared/notes-formatting.js` for the portal).
  **The note never contains HTML**: renderers escape first and convert markers
  second, so escaping keeps its injection guarantee. Two rules follow. A line is
  a portal section heading only when the *whole* line is wrapped in `**` —
  testing for `**` anywhere would swallow inline emphasis into a heading.
  Anything that *analyses* the note rather than displaying it (song title
  matching, the safety check) must read `stripNoteMarkers` output, because song
  titles are matched exactly and a stray marker fails silently. The two
  implementations live in separate repositories; change one and you must change
  the other. Unmarked notes written before this contract render unchanged.
- GitHub scheduled workflows can be disabled after long inactivity. The
  schedule-refresh and daily lesson-mirror jobs are useful, but both must be
  checked from the Overview health/operations rhythm rather than assumed
  permanent.
- **Pause planning notes → pause forecast.** `buildPauseForecast` (`lib/admin/pause-forecast.mjs`) parses pause-window dates from the `Planning_Items` notes written by `buildStructuredPausePlanningDraft` (producers: the planning pause builder, the tutor-absence bridge, and incoming-message conversion — `buildIncomingPlanningDraft` reuses the same builder when an absence message carries extracted dates and a matched student): `First lesson to pause date: YYYY-MM-DD` + `Returning from date: YYYY-MM-DD` (away period), and `Lesson date: YYYY-MM-DD` (single lesson). Parked pause items are ignored; done items can still forecast because "done" means the admin action was completed, not that the future/active pause stopped existing. If that helper's note wording changes, update the regexes/tests in `pause-forecast.mjs` — otherwise the forecast silently stops seeing those pauses (it does surface an `unparsedCount`, but only for items it recognises as pauses by title/notes).
- **Pause History → payment expectation is an explicit write.** Ordinary Overview,
  Issues, and live Stripe scans derive context and may sync `Issue_Queue`, but
  never write the Students row. `/admin/flags` first previews the deterministic
  high-confidence reconciliation plan, then requires human confirmation and a
  server-side `confirm: true` before writing `Students.payment_expectation`.
  Eligibility requires a subscription-ID Pause History match plus usual-lesson
  coverage; it never touches `setup_pending` or `inactive_or_stopped`, and never
  mutates Stripe. The confirmed run appends all
  `payment_expectation_reconciliation_attempted` events in one write, updates all
  eligible `Students.payment_expectation` cells in one batch request, then
  appends all `payment_expectation_reconciled` events in one write. Both event
  types retain the admin actor and reason. This caps the normal run at three
  Sheets write requests while leaving recoverable evidence when a
  non-transactional step fails. Duplicate Students rows for one MMS ID are one
  reconciliation decision, and every matching expectation cell is aligned.
- **Tutor absence grouped pause IDs.** `buildTutorAbsencePausePlanningBundle` creates single-date IDs as `planning_tutor_absence_pause_...` and grouped period IDs as `planning_tutor_absence_pause_period_<tutor>_<studentMmsId>_<firstDate>_<lastDate>`. When a later saved absence extends a block, the older grouped period ID is deliberately superseded and parked. Do not hard-delete those rows; finance ignores `parked`, while `Planning_Progress_Log` preserves why the visible card changed. See `docs/workflows/tutors/absence-to-pause.md` for the full workflow map.
- **Payroll period IDs.** `buildPayrollRunId` creates stable IDs from tutor short name + period start/end. Do not manually change `period_start`, `period_end`, or `tutor_short_name` on saved payroll rows; the payroll page will treat that as a different run. Use `adjustment_amount` + `notes` for corrections.
- **Wise batch-payment CSV columns.** `WISE_CSV_HEADERS` in `lib/admin/wise-helpers.mjs` is the exact column order Wise expects on batch upload: `recipientId, name, recipientEmail, recipientDetail, sourceCurrency, targetCurrency, amountCurrency, amount, paymentReference, receiverType`. `amount` (tutor's owed figure) and `paymentReference` (`FC pay <periodEnd>`, kept short for Wise's per-currency length limit) are generated; the rest come from the `Tutor_Wise` sheet. Only **reviewed** payroll rows with a positive owed amount are emitted (`buildWiseBatch`). If Wise changes its expected CSV format, update `WISE_CSV_HEADERS` + the wise-helpers tests. The dashboard only generates the file; a human uploads and approves it in Wise (payroll stays reconciliation, not execution).
- **MMS attendance statuses → payroll classification.** `resolveSlotState` in `lib/admin/payroll-helpers.mjs` maps literal MMS `AttendanceStatus` strings to pay buckets: `Present`/`Attended`/`Completed` and `AbsentNoMakeup` → **payable** (the last is absent-but-invoiced: practice-video / no-makeup policy); `AbsentNotice` → **excluded £0** (absent with notice, not invoiced); `Unrecorded`/blank → **needs review**. If MMS renames or adds an absence status, an unknown value falls safely to "needs review" (it never silently pays), but `PAYABLE_STATUSES`/`EXCLUDED_STATUSES` + the payroll tests should be updated to classify it. The mapping mirrors the tutor's own invoicing (validated against a real Kenny invoice 2026-06-27). Payroll can now resolve an unrecorded lesson in place: Present, AbsentNoMakeup (tutor paid), or AbsentNotice (£0) writes through to the exact MMS attendance row, then invalidates the payroll cache. A high/medium-confidence `Pause History` identity match whose date window covers that exact lesson is shown as evidence for the £0 decision; low-confidence/email-only matches are never presented as one-click answers. WhatsApp/pause history is evidence, the admin chooses the outcome, and MMS remains the canonical attendance record.
- **MMS attendance search `EndDate` is exclusive.** `POST /search/attendance` compares `EndDate` against `EventStartDate` at midnight, so an `EndDate` of `2026-07-07` returns **no lessons taught on the 7th**. Payroll windows are inclusive of `periodEnd` (a Wednesday run covers through the Tuesday), so `searchAttendanceForPayroll` (`lib/admin/mms.js`) shifts the bound one day forward before calling MMS; callers pass — and the cache keys on — the **inclusive** end date they mean. Do not "simplify" that away: passing `periodEnd` straight through silently drops the last day of every payroll window and every tutor statement, producing a plausible-looking but short total (this was live 26 Jun–8 Jul 2026; `tests/admin/mms-payroll-attendance.test.mjs` pins the contract). **Resolved 2026-07-19:** the search paginates (`fetchAllPages`, `lib/admin/mms-pagination.mjs`) and **throws rather than truncates** past its safety cap, so growth can no longer produce a silently short payroll. **Strengthened 2026-08-01:** completeness is now *verified*, not inferred. Every MMS `/search` response carries `TotalItemCount` (its own count of matching records), so `fetchPayrollAttendance` returns `{ rows, total }` and the walk stops at exactly that number, throwing if it ever holds a different one. The old "a page shorter than asked is the last one" rule survives only as a fallback when no total is available, and it is weaker than it looks: it assumes the endpoint honours the `limit` we send, so asking for more than a server-side cap would make *every* page look final and truncate in silence. That asymmetry is why the page size is now `PAYROLL_ATTENDANCE_PAGE_SIZE = 2000` (`lib/admin/mms.js`) rather than 1000 — with the total verified, **sizing the page is a latency decision, not a correctness one**. Raise it freely; do not lower it to 1000 believing that is safer. Measured 2026-08-01: the 35-day window is 951 rows in **one** request; a 3,229-row window pages correctly in two with no duplicates and nothing lost against a single-shot fetch; MMS honours a limit well above this (3,194 rows in one 3.1s request vs 2.3s for 1,000 — request overhead dominates, row count barely registers). Note `limit` is part of the attendance cache key, so the page size has exactly one home and query builders deliberately omit it. Invariants (pagination completeness, window tiling, Wise batch total = CSV sum, disputed exclusion) are pinned in `tests/admin/money-path-invariants.test.mjs`.
- **A pinned MMS Free event is one occurrence, not the slot.** The Waiting slot buttons carry a `freeEventId`, but `buildFreeSlotSummary` (`lib/admin/capacity-helpers.mjs`) collapses each weekly Free slot to its **soonest** occurrence, so that ID always means "this slot, in its next free week". A first lesson may therefore start any whole number of weeks after it, up to `MAX_FREE_SLOT_WEEK_OFFSET` (12) — `validateMmsFreeCalendarEvent` (`lib/admin/mms-helpers.mjs`) refuses a different weekday, an earlier date, or a further one, and `getValidatedMmsFreeCalendarSlot` (`lib/admin/mms.js`) confirms the bumped week is still an empty Free event of the same tutor, time and length before onboarding writes anything. That day lookup uses `POST /search/calendar/events`, whose `EndDate` is exclusive exactly like attendance, so it passes `lessonDate` and `lessonDate + 1`. **Removal still deletes the pinned occurrence with `DeletionType: 'Future'`, deliberately taking the free weeks between it and the first lesson.** Do not "fix" that by deleting from the bumped occurrence instead: a weekly Free slot with two or three occurrences left still reads to `buildFreeSlotSummary` as a full weekly slot, so it would be offered to a second student who then collides with this one from their third lesson onwards.
- **Payroll attendance cache.** `searchAttendanceForPayroll` caches by query params with a 10-minute TTL, a 20-minute stale-while-revalidate window, and in-flight coalescing — the same shape as the Sheets read cache in `lib/admin/sheets/core.mjs`. This exists because the payroll page is `force-dynamic` and every `revalidatePath` after a "Mark reviewed" save rebuilds the whole page, re-running a ~950-row MMS query (measured 3.6s) to redraw a preview that cannot have changed. Stale rows are served immediately and refreshed behind the request; a failed background refresh is logged, never thrown into the render. Past TTL + SWR a caller waits for fresh rows by default — **but the payroll page passes `allowExpired: true` and never waits** (2026-07-29). A save re-renders the whole page inside its own POST and the button's spinner lasts exactly that long, so crossing the 30-minute ceiling mid-session turned a ~1s save into a ~7s one (re-measured 2026-07-29: 4.7s for 951 rows, 1.2s for the five Sheets reads beside it). The page therefore renders from whatever is cached at any age and lets the refresh run behind the request; when what it served is past the ceiling it says so in the header summary (`peekPayrollAttendanceAge` → "MMS attendance from 2 hr ago, refreshing"), because cached context must show its freshness. The deliberate escape hatch is the **Refresh from MMS** button (`?refresh=1` → `forceRefresh`), used after recording a lesson in MMS; the page then redirects to a clean URL so the flag does not persist and force a refetch on every later save. A forced read must wait out and discard any older in-flight request before starting its own fetch—otherwise a post-write refresh can accidentally adopt a response that began before the attendance update. Direct payroll attendance writes invalidate the whole payroll-attendance scope and version-guard older fetches from repopulating it. Do not shorten the TTL to "keep it fresh" — a wall-clock timer fires at random points in a review session (60s was roughly one read-the-invoice-click-next cycle), which is what made the page feel randomly slow. For the same reason, do not remove `allowExpired` from the payroll page: any wall-clock boundary that can fall between loading the page and clicking save puts a human back on the slow path at the moment they are least able to explain it. The page also streams — the shell renders from the URL alone and the tutor workspace arrives behind a `Suspense` boundary (measured TTFB 0.15s against a 1.9–2.8s full render), so a cold window no longer shows a blank page.
- **One attendance query for the whole payroll lane.** `buildPayrollAttendanceQuery(payDate)` (`lib/admin/payroll-helpers.mjs`) is the single MMS query shape both the payroll page and `loadTutorStatement` use, so they share a cache key (2026-07-29). The statement previously asked for its own `{one tutor, one week}` window and therefore always paid a cold fetch, even when opened directly off the page holding the answer. Reuse is safe because **`buildPayrollPreview` filters slots by teacher and period itself** — a superset of rows is equivalent input, verified against all 37 real reviewed/paid runs with zero difference in lesson count, minutes or amount, and pinned by a test. The statement still checks `attendanceQueryCoversPeriod` first and falls back to the exact narrow window if a hand-set period sits outside the page's 35-day window: a silently short row set on a money surface is the precise failure this lane was bitten by in June 2026. Do not "simplify" that guard away.
- **Recording attendance patches the cache instead of dropping it.** `updatePayrollAttendanceStatus` used to `invalidatePayrollAttendanceCache()`, and the `router.refresh()` that follows a Present/Absent/Cancelled decision then paid a full ~950-row MMS fetch (4.7s) to learn one field the dashboard had just set. It now calls `applyPayrollAttendanceStatusToCache`, which folds the new `AttendanceStatus` into every cached window via `patchScopeStale` (2026-07-29). This is a *complete* patch for what the page shows — `AttendanceStatus` is the only field payroll classification reads (`mapAttendanceRow` → `resolveSlotState`) — and is only applied after MMS returns OK for that exact row. Patched entries are aged to **stale, not fresh**, so the next read serves them instantly and still refreshes from MMS behind the request: the patch is a head start on the truth, never a substitute for it. If the row is in no cached window the patch reports 0 and the caller falls back to invalidating, so the cache is never left asserting a state nothing reconciled. In-flight fetches that predate the write are version-guarded out, exactly as with `invalidateScope`.
- **Outbound request timeouts.** `fetch` and the Sheets client both default to *no* timeout, so a stalled connection hung the render behind it indefinitely — a spinner with no error and nothing in the logs. Every MMS call goes through `mmsFetch` (`lib/admin/mms.js`); Stripe and GitHub calls go through `fetchWithProviderTimeout` (`lib/admin/provider-fetch.mjs`); Sheets sets `timeout` once on the client. All default to **30s** and convert a hang into an explicit provider-specific error without claiming a write succeeded. `MMS_REQUEST_TIMEOUT_MS`, `STRIPE_REQUEST_TIMEOUT_MS`, and `GITHUB_REQUEST_TIMEOUT_MS` tune the fetch ceilings (milliseconds, capped at two minutes). The defaults are deliberately generous next to measured healthy calls: this is a liveness guard, not a latency target. Do not tighten them to "fail faster" without evidence—a timeout shorter than a legitimate slow response turns an inconvenience into a workflow that cannot load.
- **Blind Stripe forecast → provider reveal.** `buildStripeMonthlyForecast` (`lib/admin/stripe-forecast-helpers.mjs`) uses dashboard-owned roster/pricing plus schedule weekday and structured pause dates to estimate the current calendar month. Weekly prices are multiplied by occurrences of the student's usual weekday; fortnightly/monthly frequency weights remain approximate because the dashboard does not yet own a billing-anchor phase. Orchestra uses its monthly price. The first row for a month wins. `createStripeAmountsPostHandler` must complete `ensureMonthlyStripeForecast` before either bulk Stripe fetch begins; tests pin both the ordering and fail-closed path. After month close, `buildStripeReconciliation` compares the locked per-student items with the revealed breakdown. `netDifference` answers the headline question; `totalAbsoluteError` sums student-level misses plus unmatched Stripe money, so positive and negative mistakes cannot cancel; `offsettingError` names the amount hidden by the net. Attribution separates pause-state misses, post-lock onboarding, invoice-occurrence timing, missing invoices, price differences, inactive collections, and unmatched money. `modelAbsoluteError` removes only evidenced post-lock onboarding from the total; it does not excuse other unknowns.
- **Stripe API fields → amounts cache and live issue checks.** `mapSubscriptionToAmounts`/`summariseCollectedInvoices` (`lib/admin/stripe-amounts-helpers.mjs`) rely on: `subscription.items.data[].price.unit_amount` (pence) × `.quantity`, `price.recurring.interval`/`interval_count`, `subscription.pause_collection`, `subscription.discount.coupon.{percent_off,amount_off}`, and `invoice.{status,amount_paid,created,subscription,customer}` (with `parent.subscription_details.subscription` tolerated). Per-student collection matching prefers subscription ID; customer-only matching is accepted only when unambiguous. Live issue checks additionally expand `latest_invoice.payment_intent` to distinguish scheduled retries from authentication failures and hard declines. The `STRIPE_API_KEY` is a **restricted read key** — minimum scopes verified 2026-07-15: customers, subscriptions, invoices, prices, and Payment Intents readable; charges/payouts/balance_transactions denied (bank-level cash truth is deliberately out of reach). If the key is rotated, preserve all five read scopes: the Monday `/api/cron/stripe-amounts` refresh needs the first four, while one-student/live issue refreshes need Payment Intents Read. The cron shares `FINANCE_SNAPSHOT_SECRET` (same trust domain, same pipeline).
- **Assumptions version → snapshot notes.** Every `Finance_Snapshot` row's `notes` column carries `PRICE_ASSUMPTIONS_VERSION` (`lib/admin/finance-assumptions.mjs`). Changing any price-table/hourly-rate/VAT constant without bumping that string makes a series step-change untraceable — the constants carry bump-reminder comments.
- **Monthly finance baselines retry without rewriting history.** The monthly workflow runs on days 1–7 and `snapshot_id = fs_monthly_YYYY-MM` makes later successes no-ops once that month's row exists. `snapshot_at` is always the real capture time. If a month was genuinely missed, the comparison UI may use the earliest weekly row from that month, but it labels that weaker basis instead of presenting it as the month-start baseline.
- **WhatsApp auto-capture gate + school-side numbers.** Auto-ingested group messages (`source = whatsapp_group_auto`) are only written when the chat is `confirmed` in `WhatsApp_Group_Map` — confirming/ignoring a group in the inbox UI is therefore also the on/off switch for its auto-capture. School-side messages are detected three ways and stamp `school_replied_at`/`school_replied_by` on the nearest preceding open row instead of creating a new one: the bridge's `from_me` flag (our own account), the dashboard env `INCOMING_STAFF_PHONES` (comma-separated, any UK format; Tom's personal number), and the **`Tutor_Phones` sheet** (a tutor replying in the lesson group from their own number — `matchTutorPhone` resolves it to the tutor's name). That stamp is weak engagement evidence only: it never proves the specific item was answered and never marks it handled. New capture state is driven by explicit actionability, not `general` versus specific topic: action/reply stays open, uncertainty asks for review, and only `no_action` is auto-archived. Retention of auto-archived noise rows is an open decision — they accumulate in the sheet until pruned.
- **Managed tabs ↔ backup coverage.** `lib/admin/backup-tabs.mjs` is the single home for
  what the local backup covers: every tab in `buildManagedStateSheetDefinitions` must be
  in `BACKUP_TABS` or in `NON_BACKED_UP_TABS` with a written rebuildable-from-truth
  reason (`tests/admin/state-tab-contracts.test.mjs` enforces it). Exists because five
  non-rebuildable tabs drifted out of the backup unnoticed until the first restore drill
  (2026-07-19). The same test pins header uniqueness/snake_case and row-builder ↔ header
  agreement for the Song_* lane; `hygiene:check` prompts when any contract file here
  changes without its paired guard test. Restore procedure + SPOF register:
  [disaster recovery](../../operations/disaster-recovery.md) (`npm run restore:drill` is rehearsed,
  not aspirational).

## Shared Upsert Helper

`lib/admin/sheets.js` now contains `upsertManagedSheetRow()`, which centralises the common pattern:

1. ensure the managed sheet and required headers exist
2. read current rows
3. find the row by key
4. append if missing, update if present
5. invalidate the short in-process read cache for that sheet

This currently covers the one-row state upserts. Bulk issue sync still has custom logic because it batches appends and updates multiple rows.

## Read Cache Contract

Shared sheet reads use a short in-process cache in `lib/admin/sheets/core.mjs`.

- fresh cache window: repeat reads return immediately
- bounded stale window: recently-stale rows may render immediately while a background refresh updates the cache
- hard max age: old rows block for a fresh Google Sheets read

Dashboard-owned writes call `invalidateSheetReadCache()` for the affected tab. External writers, such as separate tools or manual Sheets edits, can therefore be briefly stale but should not remain stale beyond the hard cap. If a workflow needs immediate external truth, use an explicit refresh or a direct source read instead of relying on cached rows.

## Concurrency And Limits

Google Sheets is acceptable for the current scale because writes are low-volume and mostly human-triggered. The main risk is two users editing the same keyed row at nearly the same time. Sheets remains last-write-wins: there is no compare-and-swap row primitive. Student mutations therefore force-read before locating an MMS ID, single-student edits write only the named cells, and archive/delete re-locates the MMS ID after the archive append before deleting. Shared managed-row upserts also bypass the read cache before targeting a row. These measures prevent stale cache use and greatly narrow unrelated-field collisions, but they are not a transaction; preserve the explicit partial-success handling in multi-system workflows.

The PostgreSQL Practice Chat claim is the exception: its unique key is an atomic
execution lock. A row left `claimed` for 15 minutes is never recycled. The next
matching request atomically changes it to `tracking_failed`, mirrors manual
follow-up into `Practice_Notes_Log`, and performs no provider action because the
earlier MMS/Gmail outcome is unknown.

The PostgreSQL lesson mirror is the other explicit exception. One advisory-locked
transaction upserts a provider-complete series/event/participation snapshot and
its changed-state revisions, then marks the sync successful. A secret-gated daily
job reads 14 London calendar days back through 42 days ahead, and the authenticated
`/admin/lessons` page reads aggregate parity evidence. Tutor Changes also reads a
bounded, fail-open lesson timeline from rows re-seen by the latest successful run,
but assignment and `Schedule_Context` still own relationship phase and no
operational workflow depends on the mirror. It has no MMS writer. Incomplete or
failed runs never replace the last verified snapshot or infer missing/cancelled
lessons; retry the bounded read instead.

Use append-only tabs for history (`Event_Log`, `Planning_Progress_Log`, archives). Use keyed upserts for current workflow state.

Watch for:

- duplicate keys caused by manual sheet edits
- stale browser tabs overwriting a newer state row
- wide bulk syncs taking longer than expected
- state rows drifting from external truth when MMS/Stripe/registry changes outside the dashboard
- append-only logs containing student/parent data that must stay out of git and public storage

If those become real operational problems, the next hardening step is per-row revision metadata or moving high-write workflow state to a small database. Do not introduce that until Sheets becomes a measured bottleneck.

## What Not To Store Here

- live Stripe truth
- live MMS schedule truth
- MMS attendance/completion truth
- canonical student contact truth
- registry/portal config truth
- AI decisions as authoritative state
